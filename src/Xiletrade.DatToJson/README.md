### What is Xiletrade.DatToJson?
A console tool that generates the json files consumed by [Xiletrade price checker](https://github.com/maxensas/xiletrade) from the Path of Exile 1 and 2 game files,
and keeps its DAT schemas up to date by itself after a game update.

It reads `.datc64` files by itself and depends on [libGGPK3](https://github.com/aianlinb/LibGGPK3) to get them,
either from a local `Content.ggpk` or directly from the patch CDN of the game (no installation needed).
Game bundles are decompressed with [ooz](https://github.com/zao/ooz), an open source decompressor built from source (see below): no proprietary library is used.
Json models and serializer come from Xiletrade.Library, so the application reads the files exactly as they are written.

### The two versioned files
| File | Content | Written by |
|---|---|---|
| `Schemas/poe<game>.schema.json` | Minimal schema: for each table, only the columns actually read, with their byte offset in a row and their type, plus the row length of the calibrated game version. | You (first time or manual fix), `calibrate`, `update`, `fullupdate` |
| `Schemas/poe<game>.snapshot.bin` | Fingerprints (64-bit hashes) of every value read with this schema, on one game version. No game text. Generated by the tool, it is not a game file. | `snapshot`, `calibrate`, `update`, `fullupdate` |

They always go together: the snapshot describes what the schema reads on a given game version.
Commit them together, with the json files they produced.

### Commands
```
Xiletrade.DatToJson <snapshot|calibrate|export|update|fullupdate> --game <1|2|all>
                    (--ggpk <Content.ggpk> | --cdn <current|url> [--cache <directory>])
                    [--schemas <directory> | --schema <file> --snapshot <file>]   (default: src/Xiletrade.DatToJson/Schemas)
                    [--output <directory>] [--report <file.md>] [--diff <file.diff>]
```
| Command | What it does | Writes |
|---|---|---|
| `snapshot` | Reads the english DAT files with the schema as is, checks every value, writes the snapshot. | snapshot |
| `calibrate` | Finds the used columns again in the new DAT files, by comparison with the snapshot. | schema + snapshot, only if every column was found |
| `export` | Writes the json files of every language with the schema as is, after comparing each one with the previous generation. Refuses to run when a file does not have the row length of the schema. | `<output>/<culture>/*.json`, diff |
| `update` | `calibrate`, then `export` when the calibration succeeded. | all of the above |
| `fullupdate` | **Every step, the command to run after each game update**: `snapshot` when a game has none yet (first run), `calibrate`, `export`, and the differences of the json files written **in the report**. `--report` is required. | all of the above + report with the diff |

Games:
* `--game 1` or `--game 2` : one game. `--game all` : PoE 1 then PoE 2 in one run, with one report and one diff.
PoE 2 is run even when PoE 1 failed; the exit code is the worst of both. `--game all` needs `--cdn current`.

Schemas and snapshots:
* **By default**, the `Schemas` folder of this project (`src/Xiletrade.DatToJson/Schemas`): the versioned files are read and updated in place,
nothing to pass. The build gives this path to the executable (`RuntimeHostConfigurationOption` in the project file).
* `--schemas <directory>` : another folder of `poe1.schema.json`, `poe1.snapshot.bin`, `poe2.schema.json`, `poe2.snapshot.bin`.
* `--schema <file>` and `--snapshot <file>` : the two files one by one, for a single game.

Game files (one of them is required):
* `--ggpk <path>` : a local `Content.ggpk`.
* `--cdn current` : the patch server of the game gives the CDN url of its current version, then only the needed bundles are downloaded.
* `--cdn <url>` : a versioned CDN url, as printed by `--cdn current` (`https://<cdn host>/<version>/`), to target a given version or if the patch server can not be reached.
* `--cache <directory>` : where the downloaded bundles are kept, one folder per game version.
By default `bin/ooz/temp/poe<game>` in the project folder (not the temp folder of the system), **emptied once `export` or `update` has written the json files**;
after `snapshot` or `calibrate` it is kept, so a following command on the same version downloads only the index again.
A folder given with `--cache` is never emptied.

Outputs:
* `--report <file.md>` : markdown report of every game: calibration (each column with its status), export, and the json changes.
Each game ends with the source of the game files (path, or CDN version and url). With `fullupdate`, the report also contains
the full diff of each game in a `diff` block (`## PoE <game> json diff`, "No change." when nothing changed): it can be long.
* `--diff <file.diff>` : the same differences in a separate file (export, update, fullupdate), see below.

Exit codes : `0` success, `1` manual action required (nothing was written for that game), `2` error (message displayed).

Other defaults: `--output` is `Data/Lang` next to the executable, so **pass `--output Xiletrade/Data/Lang`** to update the files of the repository
(see [Workflow](#workflow-commands-run-from-the-repository-root) for the copy to `src/Xiletrade.Library/Data/Lang`).
The executable also has a copy of `Schemas`, made at build time: it is only used when the tool runs without the path given by the build (e.g. published elsewhere).

### Json changes (diff)
Before replacing a json file, `export` and `update` compare it with the previous generation:
* a file identical to the previous one is **not written again**;
* the report lists the new and changed files, with the number of entries removed and added;
* the differences are written in the **git unified format**, readable in any diff viewer or in a pull request:
in the report with `fullupdate`, in a file with `--diff`.

The json files are written on a single line, so a plain `git diff` shows one huge changed line.
The diff of this tool shows **one entry per line** (one mod, one base, one word...), and **only the changed entries**, without context (like `git diff -U0`), so the report stays small:
```diff
diff --git a/de-DE/ItemClass.json b/de-DE/ItemClass.json
--- a/de-DE/ItemClass.json
+++ b/de-DE/ItemClass.json
@@ -89,0 +90 @@
+{"id":102,"id_origin":"CursedDucat","name":"Verfluchte Dukate","name_en":"Cursed Ducat"}
```
Line numbers are entry numbers: `@@ -89,0 +90 @@` adds entry 90 after entry 89, `@@ -25 +26 @@` replaces entry 25, which becomes entry 26.
An empty diff means that nothing changed. Without context, `git apply` needs `--unidiff-zero` to apply such a diff.
Entries are compared on their raw bytes (Myers algorithm, the default one of git); above 4000 changed entries in a file, the file is shown as entirely replaced.

### Workflow (commands run from the repository root)
**After each game update**, one command does every step for both games:
```
dotnet run --project src/Xiletrade.DatToJson -c Release -- fullupdate --game all --cdn current --output Xiletrade/Data/Lang --report datToJson-report.md
```
The json files are written to `Xiletrade/Data/Lang`, the folder downloaded by the Xiletrade clients from master (data update of the application).
They are also needed in `src/Xiletrade.Library/Data/Lang` (files shipped with the application): when the exit code is `0`, copy there **only the files written by the run**
(unchanged files are not rewritten, so git lists them). Hand-made files of the same folders (`ParsingRules.json`, chinese files of the Tencent client) are never copied:
```bash
git ls-files --modified --others --exclude-standard -- Xiletrade/Data/Lang | while IFS= read -r file; do
  target="src/Xiletrade.Library/Data/Lang/${file#Xiletrade/Data/Lang/}"
  mkdir -p "$(dirname "$target")" && cp "$file" "$target"
done
```
Schemas and snapshots are read and updated in `src/Xiletrade.DatToJson/Schemas` (default of `--schemas`). For each game, PoE 1 then PoE 2:
1. **snapshot**, only when the game has none yet (first run): created from the schema as is, check the first values shown in the report;
2. **calibrate**: the used columns are found again after the game update, the schema and the snapshot are rewritten;
3. **export**: every json file is compared with the previous one, then written when it changed;
4. **report**: calibration, export, changed files, and the diff of the json files.

Then `git status` shows the moved offsets, the new snapshots and the regenerated json files (both folders); the report shows what changed in them.

**When the exit code is `1`**: open the report, it names the column that was not found and the best candidate offsets.
Fix the offset (or the type) in the schema by hand, run `snapshot` to accept the fix, then `fullupdate` again.
Each step also exists as a separate command (`snapshot`, `calibrate`, `export`, `update`).
Use `--game 1 --ggpk <path>` (or `--game 2`) instead of `--game all --cdn current` to read a local installation.

### GitHub workflow
`.github/workflows/dat-to-json.yml` runs the same steps on a Windows runner (CMake, a C++ compiler and git are installed there, ooz is built by the first build),
started by hand (`workflow_dispatch`, a schedule is ready to uncomment):
1. `fullupdate --game all --cdn current --output Xiletrade/Data/Lang`, the report is uploaded as the `datToJson-report` artifact;
2. exit code other than `0`: the job fails, **nothing is committed** (with `--game all`, the other game may have been written);
3. copy of the written files to `src/Xiletrade.Library/Data/Lang`, as above;
4. no change: the job ends. Otherwise the tests run with the new files, then a pull request **to dev** is opened (or updated) from the `datToJson/update` branch,
with the json files of both folders and the schemas and snapshots, and the report as description.

Protections, because `Xiletrade/Data/Lang` on master is downloaded by every client: a generated file reaches users as soon as it is on master.

| Protection | Why |
|---|---|
| Pull request to dev, never a push | A human reads the report and the diff before the merge; master only receives it with the next dev merge |
| Stop on exit code `1` or `2` | A column not found or an error never produces a commit, even when the other game succeeded |
| Tests in the workflow | A pull request opened with `GITHUB_TOKEN` does not start `CI.yml`. To start it too, give a personal access token (or a GitHub App token) to `token:` of `create-pull-request` |
| `add-paths` limited to the three folders | The report and the build files are never committed |
| `concurrency` | Two runs never update the same branch at the same time |
| `if: github.repository == 'maxensas/xiletrade'` | Never runs in a fork |
| `permissions` | Only what the pull request needs (`contents`, `pull-requests`) |

The description of a pull request is limited to 65536 characters: when the report is longer, the diff blocks are left out of it, the full report stays in the artifact.

**Before the first run**: `Xiletrade/Data/Lang` still holds an older generation of the PoE 1 bases, mods and monsters, with an `inherits_from` field
that the application no longer reads (removed when the client saves the downloaded file). The first run removes it from every entry, so its diff is the whole files.
To keep the first diff readable, align the folder once in a separate commit (same entries, without this field):
```bash
for culture in de-DE en-US es-ES fr-FR ja-JP ko-KR pt-BR ru-RU th-TH zh-TW; do
  for file in Bases Mods Monsters; do cp "src/Xiletrade.Library/Data/Lang/$culture/$file.json" "Xiletrade/Data/Lang/$culture/"; done
done
```

### What is updated automatically
| Change made by a game update | Result |
|---|---|
| Columns added, removed or resized **before or between** the used columns, including before the key | Offsets found again, schema and snapshot rewritten |
| Columns changed **after** the last used column | Only the row length changes |
| Rows added, removed or reordered, values reworded | Absorbed (scores are computed on rows joined by key) |
| A used column changes type, disappears or changes meaning | **Manual**: code `1`, nothing written, candidates in the report |
| Two used columns swap their order | **Manual**: code `1` |
| Two offsets match almost as well (e.g. `Text` / `Text2` of words) | Lowest offset kept (columns keep their order), reported as **ambiguous**: check it before committing |

### How a column is found again
1. The key column (e.g. `Id`) is first read at its current offset. If its values no longer match the snapshot,
every offset of the row is tried and the one whose values best match the old keys is kept.
2. Old and new rows are joined on this key.
3. Every other column is read at its current offset, otherwise every offset after the previous column is tried:
the one that best gives back the old values on the joined rows is kept.
4. The chosen offset is checked on every row (valid string reference, valid foreign row...).

Foreign rows are compared through the key of the referenced row, because row indexes change when rows are inserted.
Thresholds: at least 75% of the keys read must exist in the snapshot (a patch adds rows), and 90% of the values must match.

### Native decompressor (ooz)
Path of Exile 1 and 2 store their files in bundles (`*.bundle.bin`, and the `_.index.bin` index) compressed with the Oodle formats (Kraken, Mermaid, Leviathan...).
Every game file must be decompressed before it can be read, whether it comes from `Content.ggpk` or from the patch CDN.

libGGPK3 expects the proprietary Oodle library (`oo2core`), which is not shipped with it. This tool uses ooz instead:
* [ooz](https://github.com/powzix/ooz) is an open source implementation of the Oodle decompressors, licensed under GPL v3.
The maintained, portable fork [zao/ooz](https://github.com/zao/ooz) is used.
* Its sources are **not copied** in this repository: `Native/CMakeLists.txt` downloads them at a pinned commit and builds a small `ooz` library
(`ooz.dll` on Windows, `libooz.so` on Linux), decompression only.
* `Native/oodle_shim.cpp` exposes on top of ooz the three functions libGGPK3 calls to read bundles, with their Oodle names and signatures.
It decodes into its own buffer then copies, because ooz may write up to 64 bytes after the end of its output.
* `OozLibrary.cs` redirects the requests of libGGPK3 for `oo2core` to this library (`NativeLibrary.SetDllImportResolver`), so libGGPK3 is used unchanged.
* Only decompression is used: the tool never writes or recompresses game files.

**Nothing to do by hand**: when `bin/ooz/lib/ooz.dll` (`libooz.so` on Linux) is missing, the build of the project runs CMake first
(`Xiletrade.DatToJson.csproj`, target `BuildOoz`), then copies the library next to the executable. This only happens on the first build:
the next builds find the library and skip this step.

Everything CMake produces goes to the `bin/ooz` folder of the project, ignored by git: the source folders are never modified,
and the ooz sources are never updated (downloaded once at the pinned commit). Once the library is built, **only `bin/ooz/lib/ooz.dll` is kept**:
the downloaded sources and the files generated by CMake are deleted. Delete `bin/ooz/lib` to force a rebuild of ooz.

Requirements for this first build: CMake 3.20+, a C++17 compiler and git (on Windows, Visual Studio with the C++ workload is enough:
when CMake is not on the PATH, the one installed with Visual Studio is used). `-p:OozCMake=<path>` selects another CMake.
If no CMake is found, the build stops with an explicit message. `dotnet build -p:SkipOozBuild=true` builds the project without ooz:
the tests run, but every command then stops with code `2` and says the library is missing.

### Limitations
* ooz does not check the integrity of the data (no CRC, like libGGPK3's use of Oodle): a corrupted bundle in the cache may give garbage instead of an error.
The row length checks and the calibration scores usually catch it.
* With `--ggpk`, only a `Content.ggpk` is supported (not a Steam installation with a `Bundles2` folder): use `--cdn` instead.
* If a download was interrupted and a bundle in the cache is broken, delete `bin/ooz/temp` (or the folder given with `--cache`).
* The redirection to ooz was not tested with a Native AOT publication: run the tool with `dotnet run` or the normal build.
